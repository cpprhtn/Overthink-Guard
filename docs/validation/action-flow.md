# 구독제: 행동의 흐름으로 헛도는 작업을 가려낼 수 있는가

- 작성: 2026-09-30, 측정 전에 고정한다.
- 계기: Claude Code는 생각 내용을 실시간으로도, 끝난 뒤에도 주지 않는다. 헤드리스 Sonnet 기록의 thinking 텍스트는 0자이고, 그 밖의 기록도 최대 311자 조각이다. 그래서 생각의 흐름은 볼 수 없다. 대신 도구 호출, 명령, 파일 읽기·수정, 도구 실패는 일어나는 즉시 세션 기록에 적힌다. 코딩 작업의 오버엔지니어링과 헛돌기는 이 **행동의 흐름**에 드러난다는 가설을 검증한다.
- 두 단계로 나눈다.
  - A: 실제 기록 분석(무료). 쓸 만한 신호를 추린다.
  - B: 통제 실험(구독 사용). 신호가 뜰 때 끊지 않고 훅으로 방향을 틀어 준다(아래, 별도 사전 등록).

## A. 실제 기록 분석

- 데이터: 이 PC의 `~/.claude/projects` 중 사람이 직접 쓴 세션(LiteDeck, Overthink-Guard, memo). 실험용 헤드리스 세션(스크래치 경로)은 뺀다. 메시지 텍스트는 출력하지 않는다.
- 턴: 사람이 쓴 프롬프트부터 다음 프롬프트 직전까지. 도구 결과, 메타 레코드, 로컬 명령, 중단 표시는 새 턴으로 보지 않는다.
- **라벨 (사용자가 멈추게 했나):** 턴 안에 `[Request interrupted by user]`(Esc) 또는 `[Request interrupted by user for tool use]`(도구 실행 거절)가 있으면 양성이다.
  - 보조 라벨로 다음 프롬프트가 정정으로 시작하는 경우도 따로 보고한다. 정정 표현은 `아니`, `아냐`, `그게 아니`, `잠깐`, `그만`, `멈춰`, `no`, `stop`, `wait`, `don't`이다.
- **신호 (턴 안에서 그 시점까지의 기록만으로 계산. 실시간으로 쓸 수 있어야 한다):**

| 신호 | 발동 조건 |
| --- | --- |
| same_fail | 같은 도구·같은 입력이 2번 이상 실패 |
| repeat_cmd | 같은 Bash 명령을 3번 이상 실행 |
| reread | 같은 파일을 3번 이상 Read |
| errors3 | 턴 안의 도구 실패가 3번 이상 |
| err_streak3 | 도구 실패가 3번 연속 |
| edit_spread | 서로 다른 파일 8개 이상 수정 |
| edit_churn | 같은 파일을 6번 이상 수정 |
| 기준선 tools40 | 도구 호출 40번 이상 (양 기반) |
| 기준선 time10 | 프롬프트 뒤 10분 경과 (시간 기반) |

- 발동은 양성 턴이면 중단 **이전**에 일어나야 탐지로 센다. 중단 이후에만 발동하면 탐지로 세지 않는다.
- **보고:** 신호별로 발동 턴 수, 정밀도(발동한 턴 중 양성 비율), 재현율, lift(정밀도 / 전체 양성 비율)를 낸다.
- **B로 가져갈 신호의 기준:** 발동 턴이 5개 이상이고, lift가 2 이상이며, 두 기준선(tools40, time10) 중 lift가 높은 쪽보다 lift가 높을 것.
- **한계:** 양성은 35턴뿐이다. 사용자가 끊지 않은 턴이 "헛돌지 않았다"는 보장도 없다. 인내심이 있었을 수 있다. 그래서 A는 탐색이다. 효과 판정은 B에서 한다.

- **B로 가져갈 신호: `errors3`, `same_fail`.** 사전 기준(발동 5턴 이상, lift ≥ 2, 기준선보다 높음)을 넘었다. 다만 실제로 맞힌 턴이 2개, 1개뿐이라 증거는 약하다.
- **시간과 양은 사용자가 끊는 시점을 예측하지 못했다.** 10분과 40회 기준선의 lift는 1 미만이다. 사용자는 오래 걸리는 턴을 끊지 않았다. 구독 V7의 결론("긴 턴은 대개 필요한 작업")과 같은 방향이다.
- 사용자가 끊은 18턴 중 6턴은 프롬프트 뒤 22초 안, 도구 호출 0–2회 때였다. 헛돌아서가 아니라 마음을 바꾼 경우로 보인다. 흐름 신호가 중단보다 먼저 뜬 것은 3턴이다.
- 정정 표현까지 합친 보조 라벨(38턴)에서도 `errors3`, `same_fail`의 lift는 2.1–2.2로 가장 높았다.

## B 사전 등록: 헛돌 때 끊지 않고 방향을 틀어 주면 정답을 지키면서 낭비가 줄어드는가 (2026-09-30, 측정 전)

- **방법:** 헤드리스 `claude -p --model sonnet`에 작은 코딩 과제를 준다. 채점은 에이전트가 볼 수 없는 숨은 테스트로 한다. 과제는 `bench/spikes/action_flow_tasks.py`, 실행은 `bench/spikes/action_flow_live.py`다.
- **두 조건:**
  - 대조: 훅이 기록만 한다.
  - 넛지: A에서 고른 신호가 뜨면 훅이 `additionalContext`로 메모를 넣는다. 턴은 끊지 않는다(V7에서 끊으면 생각이 사라져 정답을 잃었다).
  - 두 조건 모두 같은 훅이 돌아서 오버헤드는 같다.
- **신호:** `errors3`(이 실행에서 도구 실패 3번째) 또는 `same_fail`(같은 도구·같은 입력이 2번째로 실패). `PostToolUseFailure` 훅에서 센다. 넛지는 실행당 최대 2번이다.
- **넛지 문구 (고정):** "[Overthink Guard, a monitor the user runs on this session] {이유}. Retrying the same thing rarely helps. Before the next attempt, state in one or two sentences what the error tells you about the cause, then change approach. If it truly cannot be done in this environment, say so."
  - {이유}는 `3 tool calls have failed in this task` 또는 `the same command has now failed twice`이다.
- **과제 8개:**
  - 대조군 성격의 쉬운 버그 1개
  - 원인이 다른 파일에 있는 버그
  - 없는 모듈을 쓰는 코드
  - 반올림(half-up)
  - 깊은 재귀
  - 로그 파싱 정규식
  - 영업일 계산
  - pytest가 없는 환경에서 pytest 스타일 테스트
- **반복과 제한:** 과제마다 조건별 3회, 총 48회. 동시 실행 3개, 한 실행 최대 10분(넘으면 실패로 센다).
- **허용 도구:** Read, Edit, Write, Glob, Grep, Bash. `pip`, `brew`, `curl`, `sudo`는 금지한다(사용자 시스템 보호).
- **B1 정답 보존 (합격 조건):**
  - FP 과제 0개. FP 과제는 대조가 3회 중 2회 이상 통과했는데 넛지가 1회 이하로 통과한 과제다.
  - 넛지 전체 통과 수 ≥ 대조 전체 통과 수 − 1.
- **B2 낭비 감소 (합격 조건):** 신호가 뜬 실행만 보고, 신호 이후의 도구 실패 수와 신호 이후 걸린 시간의 평균이 넛지 쪽에서 대조의 80% 이하일 것. 대조에서도 신호 시점은 기록한다.
- **판정 불가:** 조건별로 신호가 뜬 실행이 6회 미만이면 B2는 판정하지 않고 수치만 보고한다.
- **함께 보고:** 실행당 도구 호출 수, 도구 실패 수, 걸린 시간, 출력 토큰, 신호 발동률, 모델이 넛지를 의심하거나 무시한 사례.

- `otg claude-code watch`가 턴마다 도구 실패를 세고, `same_fail`이나 `errors3`가 뜨면 기록만 한다.
  - 기록 위치: `~/Library/Application Support/overthink-guard/claude-code-flow.jsonl`
  - 기록 내용: 세션 id, 시각, 이유, 실패 횟수. 명령과 텍스트는 없고, 같은 호출인지는 해시로만 비교한다.

- `otg claude-code report`가 신호 뒤에 무슨 일이 있었는지 요약한다: 사용자가 그 턴을 끊었는지, 그 뒤의 도구 호출과 실패 수, 걸린 시간.
- Claude Code는 기본 설정에서 30일이 지난 대화 기록을 지운다(`cleanupPeriodDays`). 그 전에 `report`나 `bench/spikes/action_flow.py`로 확인한다.
- 판정 기준은 A와 같다. 신호 뒤에 사용자가 끊거나 정정한 비율을, 신호가 없는 턴의 비율과 비교한다. 신호가 뜬 턴이 30개 이상 모이면 다시 본다.

## B-hard 사전 등록: 실제 저장소의 어려운 버그 (2026-09-30, 측정 전)

B의 과제는 너무 쉬워서 신호가 한 번도 뜨지 않았다. 같은 설계를 실제 버그로 다시 한다.

- **과제 12개:** 의존성 없는 순수 파이썬 저장소(cachetools, boltons, more-itertools, humanize, pyparsing, idna)의 실제 버그 수정 커밋에서 SWE-bench 방식으로 만들었다.
  - 작업 공간은 수정 직전 코드이고, `.git`은 없다. 수정 커밋에서 추가된 테스트는 빼 두었다.
  - 지시문은 이슈 설명이고, 끝에 "`python -m pytest`로 테스트할 수 있다"를 붙였다.
  - 과제마다 원래 코드로는 채점이 실패하고, 실제 수정을 적용하면 통과하는지 확인했다. 과제 생성은 서브에이전트가 했고, 12개 중 4개는 직접 다시 돌려 확인했다.
  - 과제 목록과 한 줄 설명은 B-hard 결과에 적는다.
- **통과 조건:** 에이전트가 끝낸 작업 공간 위에 숨은 테스트 파일을 덮어쓰고, 수정 전 실패하던 테스트(`grade_command`)와 그 테스트 파일 전체(`regression_command`)가 모두 통과해야 한다.
- **환경:**
  - pytest만 설치한 실험용 가상환경을 `PATH` 앞에 둔다. 사용자 시스템에는 아무것도 설치하지 않는다.
  - src 구조 저장소는 `PYTHONPATH`를 미리 잡아 둔다.
  - pyparsing 과제 3개에는 수정과 무관하게 실패하는 보이는 테스트가 하나 있다(railroad 패키지 없음). 그대로 둔다.
- **주의:** Claude Code는 0이 아닌 종료 코드로 끝난 Bash 명령(실패하는 테스트 실행 포함)을 도구 실패로 센다. 그래서 같은 테스트 명령을 두 번 실패하면 `same_fail`이 뜬다. 신호 정의는 B와 같게 둔다.
- **반복과 제한:** 과제마다 조건별 3회, 총 72회. 동시 실행 3개, 한 실행 최대 15분.
- **넛지 문구, 허용·금지 도구:** B와 같다.
- **판정 기준:** B와 같다.
  - B1: FP 과제 0, 넛지 통과 수 ≥ 대조 통과 수 − 1
  - B2: 신호가 뜬 실행에서, 신호 이후의 실패 수와 시간이 대조의 80% 이하
  - 조건별로 신호가 뜬 실행이 6회 미만이면 B2는 판정하지 않는다.
