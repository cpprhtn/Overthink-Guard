# 구독형(Claude Code) 검증 계획과 결과

- 작성: 2026-09-30, 측정 전에 기준을 고정한다.
- 대상: `otg claude-code watch` (침묵 시간 알림), `otg claude-code report` (사용량 리포트)
- 전제(S4): Claude Code는 생각 도중의 thinking 내용을 노출하지 않는다. 그래서 알림은 시간 기반이며, "모델이 실제로 오래 작업 중인가"를 맞히는 것이 목표다. "지금 끊으면 답이 맞는가"는 이 신호로 판단할 수 없다(검증 V6에서 따로 본다).

### 측정 전에 정한 세부 사항 (2026-09-30, 측정 전 추가)

- V1 라벨: 알림이 속한 "대기 구간"을 무엇이 끝냈는지로 정한다. 대기는 사용자 프롬프트, 또는 병렬 도구 호출의 마지막 결과에서 시작한다. 압축은 대기를 시작하지도 끝내지도 않는다. 모델 출력으로 끝났으면 정탐이다. 사용자가 Esc로 끊었으면 그때 모델은 일하고 있었으므로 정탐이다. API 오류, 새 프롬프트, 기록 끝은 오탐이다. 계획의 "다음 레코드가 assistant" 규칙보다 이쪽이 명세와 맞다. 두 규칙의 차이(인터럽트를 정탐으로 셈)는 결과에 따로 적는다. 기준 30초와 120초도 같이 보고한다.
- V2 기준: 20초(실험 시간을 줄이려고). (a)는 한 번에 30초 넘게 생각한 문제 3개. 알림을 받아야 하는지는 그 세션 기록의 V1 정답 규칙으로 정한다. (d)는 8초에 SIGINT를 보낸다.
- V6 문제: `bench/data/math_d_qwen3_2026-09-30.json`의 30문제(OpenR1 held-out 100–129) 가운데 qwen3가 thinking 토큰을 가장 많이 쓴 12개. 모델은 `--model sonnet --effort high`, 도구 없이 "숫자만 답하라"고 요청한다. 조기 종료 쪽은 20초에 SIGINT를 보낸다. 그 턴이 실제로 끊겼을 때만 `--resume`으로 "Stop analysing. Give your best answer now from the reasoning so far. Reply with only the final number."를 한 번 보낸다. 20초 전에 끝난 문제는 "끊기지 않음"으로 따로 센다.

### V7 사전 등록: 60초에 끊으면 정답을 잃는가 (2026-09-30, 측정 전)

V1–V6은 "알림 시점에 모델이 아직 일하고 있었나"만 쟀다. "그때 끊어야 했나"는 재지 않았다. V6는 표본이 1건이었고, 끊은 쪽이 같은 실행이 아니라 새 실행이라 중단 효과와 표본 편차를 가를 수 없었다. V7은 반복 실행으로 이 둘을 가른다. 스크립트는 `bench/spikes/subscription_paired.py`.

- **질문 1 (정답 보존):** 레시피대로 60초 알림에 SIGINT를 보내고 후속 지시를 한 번 하면, 끝까지 두는 것보다 정답이 줄어드는가?
- **질문 2 (폭주 가설):** 출력 없이 300초 넘게 가는 턴은 대부분 오답인가?
- **문제 풀:** 로컬 OpenR1 캐시 1,000행 중 조건을 모두 만족하는 문제.
  - 정수 답이고 객관식이 아니며(`question_type`이 `math-word-problem`), 문제가 400자 미만이다.
  - 데이터의 R1 풀이 중 하나 이상이 정답이다(정답 표기를 믿을 수 있게).
  - 이 조건을 만족하는 문제를 R1 풀이 평균 길이가 긴 순서로 본다.
- **선별:**
  - 순서대로 끝까지 한 번 실행한다(선별 실행).
  - 그 실행에서 출력 없는 대기가 60초 이상이면(V1 규칙) 적격이다.
  - 적격 문제는 "끝까지" 3회, "60초 중단" 3회를 더 실행한다.
  - 적격 10개가 되거나 후보 60개를 보면 멈춘다.
  - **수정 (2026-09-30, 선별 15개 뒤, 적격 0개일 때):** Sonnet은 이 문제들을 대부분 몇 초 만에 풀어서 후보 60개로는 적격이 모자랄 것으로 보였다. 그래서 후보 상한을 200개로 올렸다. 선별은 정답 여부가 아니라 대기 길이만 보므로, 이 수정은 질문 1의 결과를 보지 않고 정한 것이다.
- **60초 중단 쪽:** 실제 `ClaudeCodeObserver`(기준 60초)가 알림을 내면 그 세션에 SIGINT를 보낸다. 턴이 실제로 끊겼을 때만 `--resume`으로 V6와 같은 후속 지시를 한 번 보낸다. 알림 전에 끝나면 그 답을 그대로 쓴다. 정책 전체("60초에 끊는다")를 평가하는 것이기 때문이다.
- **끝까지 쪽:** 끊지 않는다. 20분이 넘으면 강제로 끝내고 오답(폭주)으로 센다.
- **공통 조건:** `--model sonnet --effort high`, 동시 실행 3개. 채점은 응답의 마지막 정수와 정답의 일치 여부로 한다.
- **선별 편향 처리:** 선별 실행은 "길었던 실행"이라 골라진 것이므로 질문 1의 비교에서 뺀다. 질문 1은 새로 돌린 끝까지 3회와 중단 3회만 비교한다. 질문 2에는 모든 끝까지 실행을 쓴다.
- **질문 1 합격 기준** (자동 중단을 권장할 근거):
  - 중단 쪽 정답 수 합계 ≥ 끝까지 쪽 정답 수 합계, 그리고
  - FP 문제가 0개. FP 문제는 끝까지 쪽이 3회 중 2회 이상 맞혔는데 중단 쪽은 1회 이하로 맞힌 문제다.
  - 불합격이면 "알림만, 판단은 사용자"를 유지하고, 레시피에 결과를 경고로 적는다.
- **질문 2 판단 기준:** 끝까지 쪽 실행을 출력 없는 대기 길이로 나눈다(60–300초, 300초 이상). 300초 이상이 5회 이상이고 그 정답률이 20% 이하면, 긴 기준의 "폭주 의심" 알림 단계를 검토할 근거로 본다.
- **함께 보고:** 끊긴 턴 단위의 혼동행렬(끊은 뒤 답 맞음/틀림 × 그 문제의 끝까지 다수결 맞음/틀림), 걸린 시간, 출력 토큰. 끊긴 턴 자체의 토큰은 기록되지 않으므로 후속 턴만 셀 수 있다.

### 검증하면서 찾아 고친 관찰기 버그

V1 첫 실행은 정밀도 73.4%로 불합격이었다. 오탐을 하나씩 보니 대부분 라벨 문제(압축, Esc 중단)였지만, 진짜 버그도 네 가지 있었다. 모두 고치고 테스트를 추가했다.

1. **병렬 도구 호출**: 도구 결과가 하나 올 때마다 대기를 시작했다. 모델은 마지막 결과가 와야 다시 움직인다. 이제 남은 tool_use id를 추적해 마지막 결과에서 대기를 시작한다.
2. **Esc 중단**: `[Request interrupted by user]` 뒤에도 대기가 이어졌다. 이제 중단이 대기를 끝낸다.
3. **API 오류**: `system/api_error` 뒤에도 대기가 이어졌다. 이제 끝낸다.
4. **수동 `/compact`**: 압축 요약 레코드(`isCompactSummary`)를 새 프롬프트로 보고 대기를 시작했다. 이제 압축은 대기를 시작하지도 끝내지도 않는다.

측정 도구 쪽 버그도 하나 고쳤다. 재생 시계를 `기한+0.5초`로 옮기면서 그 사이에 온 assistant 레코드를 지나쳐, 가짜 오탐 18건이 생겼다. 이제 기한 시각 그대로 poll한다.

### V3 상세

17회 모두 `(응답 수, thinking, 출력)`이 일치했다. 예: (2, 63,996, 64,003), (1, 8,312, 8,616), (1, 14, 93).

### V5 상세

기준 60초에서 알림이 간 82턴의 thinking은 중앙값 4,050, p90 6,910토큰이다. 전체 응답은 중앙값 0, p90 796, p99 3,196이다. 알림은 대체로 생각을 많이 한 턴에 간다. 하지만 **19턴(23%)은 thinking이 0**이었다. 긴 도구 입력(파일 쓰기 등)을 만들거나 API가 느린 경우다. 그래서 알림 문구를 "thinking 중"에서 "출력 없이 작업 중"(`working for Ns with no output yet`)으로 바꿨다.

### V6 상세 (`bench/spikes/subscription_early_stop.py`)

- 끝까지 실행한 정답률은 8/12다. 틀린 4개는 모두 thinking 0으로 바로 답한 문제였다.
- 끊긴 1건은 출력 토큰이 4,271에서 894로 줄고 시간도 11초 줄었지만, 답이 틀렸다. 레시피 문서의 앞선 시험(5초에 끊음, 해 하나 누락)까지 합치면 **끊은 2건이 모두 틀렸다.** 표본은 작지만 방향은 분명하다. 끊긴 thinking은 세션에 남지 않아서(S4), 후속 지시는 추론을 이어받지 못하고 처음부터 짧게 다시 답한다.

### 결론과 반영한 것

1. 알림 탐지(모델이 실제로 오래 작업 중인가)는 사전 기준을 통과했다. 기본 기준 60초는 유지한다(이 PC 대기의 0.8%).
2. 구독 환경에서도 폭주 실행이 일어난다(593초, 63,996토큰). 알림의 가치가 확인됐다.
3. 하지만 **시간만 보고 끊으면 정확도가 떨어진다.** 끊긴 턴의 추론이 사라지기 때문이다. 제품 기본값(알림만, 사용자가 판단해 Esc)을 유지하고, 헤드리스 자동 중단 레시피에는 이 결과를 경고로 적었다.
4. 리포트는 끊긴 턴의 토큰을 셀 수 없다는 한계를 문서에 적었다.
